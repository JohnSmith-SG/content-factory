# Проект: content-factory

Действующая цепочка: агент сам выбирает источник → скилл Claude Code →
JSON с постами → картинка → публикация. Не концепт, а рабочий конвейер:
каждый будний день он публикует один пост в Telegram-канал.

# Тема и площадки

- **Тема:** на стыке искусственного интеллекта и корпоративного управления
  (как ИИ меняет работу советов директоров, комплаенс, риск-менеджмент —
  актуально в т.ч. для ТЭК).
- **Площадки:** два зеркальных канала с одним смыслом, разными языками —
  Telegram (русский) и Facebook (английский, для международной аудитории).

# Структура папок

- `.claude/skills/ku-ai-social/` — скилл генерации контента
- `posts/` — результат работы скилла: JSON-файлы с готовым контентом
- `images/` — сгенерированные картинки к постам (появится на шаге с MCP fal.ai)

# Правило именования файлов

```
[дата — опционально]-[тема]-[тип].md / .json
```

Пример: `2026-08-24-board-ai-oversight-social-content.json`

# Мультиагентный конвейер

Публикация постов устроена как ролевой + последовательный конвейер из
четырёх субагентов (`.claude/agents/`), которых запускает главный агент по
инструкции скилла-оркестратора `.claude/skills/content-pipeline/SKILL.md`:

1. `content-researcher` — ищет источник и пишет черновик (текст + JSON) в
   `posts/`. Картинку не трогает.
2. `image-generator` — рисует картинку по `image_prompt` из JSON, кладёт в
   `images/`. Текст не трогает. Отдельная роль специально — правка текста
   не должна тянуть за собой пересборку картинки, и наоборот.
3. `governance-reviewer` — читает черновик, выносит вердикт (read-only)
4. `telegram-publisher` — механически публикует уже одобренный пост

Одиночный пост от идеи до превью на согласование можно провести одной
командой — `/new-post [источник/тема]` (скилл `.claude/skills/new-post/`):
сама проходит ресёрч → картинку → ревью → автоправки без вопросов,
останавливается только один раз — показать готовое превью и дождаться
«да». `content-pipeline` вызывает её же при пополнении очереди (Шаг 2),
чтобы не дублировать логику.

Каждый JSON-пост в `posts/` несёт поле `"status"`:
`draft` → `reviewed` → `approved` → `published` (плюс `"published_at"`
после публикации). Статус `approved` ставит только оркестратор, вручную,
после того как пользователь одобрил HTML-превью поста в эмуляции Telegram
(`content-pipeline` Шаг 3.5) — ни один субагент не присваивает этот статус
сам, и это единственный шаг конвейера, который нельзя автоматизировать.
Это одобрение лишь ставит пост в очередь — сам факт публикации в назначенный
день (возможно, через несколько дней) выполняет сервер по расписанию, без
участия человека. Дата в имени файла — дата очереди на публикацию, не дата
источника.

Базовый список источников для ресёрча — `context/sources.md`.

# Правила автопубликации (постоянное правило проекта, с 2026-08-25)

Content-factory публикует **один пост в день, только по будним дням, строго
в 7:30 по московскому времени**, автоматически — **без дополнительного
запроса подтверждения у пользователя** — при условии, что пост прошёл весь
конвейер (Шаги 1-3.5 `content-pipeline`) и имеет `status: approved`, то есть
уже прошёл ревью И пользователь лично одобрил превью поста в эмуляции
Telegram (не просто «прошёл governance-coach» — необходимы оба условия).

**Это разрешение не распространяется на:**
- посты, принесённые пользователем напрямую, вне очереди `posts/`;
- посты со статусом ниже `approved` (`draft`, `reviewed` без одобренного
  превью) или вердиктом «НУЖНЫ ПРАВКИ» / «БЛОКИРУЮЩАЯ ПРОБЛЕМА» — для них
  действует обычное правило: показать текст и картинку, дождаться явного
  «да» именно сейчас;
- публикацию в Facebook (механизма пока нет) и любые действия за пределами
  Telegram-канала `@ai_pro_cg`.

**Норма очереди.** В `posts/` должно оставаться не менее 5 постов в резерве
(`status: approved`, дата в будущем) **после** публикации текущего дня.
Черновики (`draft`/`reviewed`) в счёт резерва не идут — резерв должен быть
уже готов к автопубликации, а не просто существовать. Очередь
актуализируется и приоритезируется заново при каждом новом входе в проект
(см. `content-pipeline` Шаг 2).

**Fast-track.** Очень свежий (первоисточник моложе 48 часов) и очень
релевантный пост из первоисточника первого эшелона (регулятор, биржа,
крупное исследовательское объединение, топ-академический форум),
прошедший ревью **без единого флага**, может встать **в начало** очереди,
а не в хвост. Тогда оркестратор сдвигает даты в именах файлов остальных
одобренных постов (и картинок) на +1 будний день и ре-синкает очередь на
сервер. Fast-track не публикует раньше следующего буднего 7:30 МСК и не
уменьшает резерв — он меряется так же (≥5 одобренных вперёд), просто хвост
очереди удлиняется на один будний день. Полное правило (порог из 6
пунктов) — `context/sources.md`, раздел «Правило fast-track»; механика
вставки — `content-pipeline` Шаг 3.6.

**Наверстывание.** Пропущенный будний слот 7:30 МСК публикуется сразу при
обнаружении, вне расписания — не переносится на завтра.

**Реальный автозапуск по расписанию** (с 2026-08-27) — работает на отдельном
VPS (см. `.claude/deploy.md`): systemd-таймер `cf-publish.timer` будит
`cf-publish.service` по будням в 7:30 МСК (04:30 UTC), скрипт публикует
самый ранний пост из `queue/` на сервере и переносит его в `sent/`.
Никакого ИИ на сервере нет — только механические вызовы Telegram Bot API
по уже одобренной очереди. Токен бота хранится только на сервере, не в
GitHub и не в этом репозитории. Пополнять `queue/` на сервере нужно вручную
при каждой активной сессии в проекте (см. «Норма очереди» выше) — сервер
сам себе новые посты не запрашивает и не генерирует.

**Картинка поста должна быть закоммичена в ветку `main` GitHub-репозитория
до его публикации** — иначе «живая» карточка актуального поста в разделе
AI:stack на карьерном сайте не сможет загрузить картинку (карточка тогда
деградирует до текстовой). Подробности — `.claude/deploy.md`, раздел
«Карточка актуального поста на карьерном сайте».

# Уборка после публикации

Как только пост получает статус `published`, сразу удали все временные и
вспомогательные файлы, связанные именно с этим постом, из `tmp/` — черновики
подписи/продолжения текста, куски base64 картинки, HTML-превью, ответы
Telegram API (`sendphoto-response.json`, `sendmessage-response.json` и
т.п.), промежуточные версии обрезанных картинок. Ориентир — дата поста в
имени файла (например, все `tmp/2026-08-31-*`).

Не трогай при этом файлы других постов в `tmp/` (по другой дате) и сам файл
поста в `posts/`, картинку в `images/` — это не временные файлы, они
остаются постоянно.

# Хранение постов в репозитории — не более 10 (правило с 2026-08-28)

В `posts/` и `images/` держим **не более 10 самых свежих постов** (по дате
в имени файла). Как только становится больше — самые старые, уже
опубликованные (`status: published`), удаляются вместе со своими
картинками. Черновики и будущие одобренные посты не трогаем — считаем от
общего числа файлов, но под нож идут только опубликованные с самой ранней
датой.

Прунинг делается при входе в проект (`content-pipeline`, Шаг 1.5), не
автоматически и не на сервере. Цель — держать размер GitHub-репозитория
под контролем (картинки ~400 КБ каждая).

Что это НЕ ломает: серверные `queue/` и `sent/` живут своей жизнью (диск
VPS больше, там своя история для кнопки «English version»). Карточка на
карьерном сайте показывает только самый свежий опубликованный пост — он
всегда в пределах 10. Сами посты остаются навсегда в самом Telegram-канале.

# Правило канала: реакции всем, комментарии только подписчикам (2026-08-27)

Ставить реакции (эмодзи) может кто угодно — стандартное поведение публичного
канала, отдельно не ограничивается. Писать комментарии в группе-обсуждении
может только тот, кто подписан на `@ai_pro_cg` — модерирует
`cf-bot-listener.service` на сервере (см. `.claude/deploy.md`), удаляя
комментарии остальных автоматически.

# Кнопка «English version» (реализовано 2026-08-27, переделано 2026-08-27)

Под каждым постом — кнопка «🇬🇧 English version». Первая версия механизма
(слово "English" в личку боту + `callback_data`-кнопка) оказалась
неудачной: `callback_query` срабатывает тихо на сервере, Telegram никуда
не переключает пользователя — со стороны выглядело так, будто кнопка не
работает, даже когда сообщение реально уходило. Заменено на стандартный
для Telegram-ботов паттерн — deep link.

Текущий механизм:

1. Кнопка — не `callback_data`, а обычная `url`-кнопка вида
   `https://t.me/ai_pro_cg_bot?start=en_<short_id>`. При нажатии Telegram
   физически открывает пользователю чат с ботом (а не просто дёргает
   сервер в фоне) — это и есть исправление исходной проблемы.
2. Бот получает `/start en_<short_id>`, проверяет подписку на
   `@ai_pro_cg` живьём через `getChatMember` и сразу присылает
   английский текст (`platforms.facebook.content`) в личку — либо
   просит сначала подписаться и нажать кнопку ещё раз.
3. Никакого постоянного списка "кто подключился" не хранится — подписка
   проверяется заново при каждом нажатии, так что если человек потом
   отпишется от канала, доступ не зависает в устаревшем состоянии.
4. Первое нажатие для человека, который никогда не писал боту, всё равно
   потребует один лишний тап по кнопке **START**, которую сам показывает
   Telegram, — это ограничение платформы, не наше решение, обойти нельзя.

Закреплённое сообщение в канале с этого момента не просит ничего писать
боту — только "подпишись на канал, кнопка сама заработает".

**Язык служебных сообщений (правило с 2026-08-27).** Закреплённое сообщение
и любое другое служебное сообщение канала, объясняющее кнопку «English
version», — всегда двуязычное (русский абзац, затем английский). Оно
адресовано ровно тем, кто не читает по-русски, поэтому русский-только текст
здесь не работает. На обычные посты канала это правило не распространяется:
они остаются на русском, английская версия — по кнопке и в Facebook.
Появилось из комментария подписчика к закрепу (`message_id` 26 → 24).

# Синхронизация при входе — автоматическая (хук, с 2026-08-28)

Механическая часть входа в проект вынесена в `SessionStart`-хук
`.claude/hooks/session-entry-sync.sh` (подключён в `.claude/settings.json`).
При старте любой сессии в этой папке он **без вопросов**:

1. `git pull --ff-only origin main`;
2. сверяется с `sent/` на сервере и проставляет `status: published`
   (+`published_at`) тем локальным `posts/*.json`, которые сервер уже
   опубликовал по расписанию;
3. если что-то изменилось — сам делает `commit` и `push` в `main`
   (сообщение с пометкой `[auto-хук]`);
4. скачивает свежий `comments_for_review.jsonl` в `tmp/`;
5. печатает сводку: время по Москве, глубина резерва (норма 5),
   пропущенные слоты, число новых комментариев.

Хук всегда завершается успешно — сеть или сервер недоступны — просто
пропускает свою серверную часть и пишет об этом.

**Что хук НЕ делает** (остаётся за Claude по скиллу `content-pipeline`):
разбор новых комментариев (Шаг 0), генерация постов при нехватке резерва
(Шаг 2), ревью, превью и одобрение (Шаги 3–3.5), fast-track (Шаг 3.6),
прунинг старых постов (Шаг 1.5). Claude при входе всё равно запускает
`content-pipeline` — хук лишь снимает с него рутину и вопросы про коммит.

# Ежедневный автозапуск из любого проекта (с 2026-08-28)

Помимо локального хука выше есть **глобальный** механизм: раз в сутки, при
первом входе в любую сессию Claude Code (в любом проекте) после 7:30 МСК,
автоматически прогоняется весь дневной цикл content-factory.

- Глобальный `SessionStart`-хук `~/.claude/hooks/cf-daily-trigger.sh`
  (подключён в `~/.claude/settings.json`): проверяет время по Москве и
  отметку `~/.claude/.cf-daily-stamp`; один раз в день просит основную
  сессию запустить фоновый агент.
- Фоновый агент выполняет скилл `~/.claude/skills/cf-daily/SKILL.md` —
  самодостаточную версию `content-pipeline` (работает по абсолютным путям,
  без проектных субагентов): синхронизация, прунинг, разбор комментариев,
  пополнение очереди при резерве < 5, governance-ревью — всё, что не
  требует человека.
- Если согласовывать нечего — агент возвращает одну строку статуса и
  завершается. Если пост дошёл до превью или комментарий спорный — агент
  отдаёт это основной сессии, та показывает пользователю, ответ
  возвращается агенту через SendMessage, агент дошивает (очередь, сервер,
  коммит) и завершается.
- Не согласовал превью за день → пост остаётся `reviewed`, ничего не
  публикуется, назавтра агент предлагает заново.

Чтобы фоновый агент не упирался в запросы разрешений из чужого проекта,
в `~/.claude/settings.json` нужны allow-правила на запись в
`content-factory/**` и на `vps.sh` / `session-entry-sync.sh` (список — в
шапке скилла `cf-daily` и в инструкции по установке).

# Права в этом проекте

Файлы внутри репозитория можно создавать, редактировать и удалять без
подтверждения. Удаление файлов за пределами репозитория и отправка любых
сообщений — только с явным подтверждением, **за исключением автопубликации
по правилам выше и авто-коммитов синхронизации из хука
`session-entry-sync.sh`**.
